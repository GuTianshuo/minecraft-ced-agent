# V2 本机训练与可视化实施规划

日期：2026-11-14（Asia/Shanghai）

> 状态：实施规划，尚未实现或压测。本文不代表已部署训练环境。以原版 Minecraft 内的可迁移行为为目标；优先实现可靠环境、数据与小模型闭环，再验证 CED。原设计中的延迟、显存、准确率和训练天数均不作为本版本性能承诺。

## 1. 硬件与核心决策

| 项目 | 已知配置 | 依据 |
| --- | --- | --- |
| CPU | Intel Core i5-12600K | 用户提供；需在 Ubuntu 核对核心拓扑与可用线程 |
| 内存 | 48 GB | 用户提供；以系统实际可用内存为准 |
| GPU | RTX 4070 Ti SUPER，16 GB | 本机 nvidia-smi 识别，16376 MiB |
| 系统 | Windows；可安排 Ubuntu | Ubuntu 是否原生、驱动和磁盘空间待部署时确认 |

**决策摘要**：

1. 优先原生 Ubuntu 24.04 LTS；Windows 保留为开发、人工示范与观战入口。双系统无法同时运行，若启动 Ubuntu，则观战客户端也在 Ubuntu 运行。WSL2 是备选，不能默认其图形和进程通信性能与原生一致。
2. 主环境固定为 Minecraft Java 1.20.1 + Fabric + Carpet 1.4.112 + JDK 17。Fabric Loader、Fabric API（如使用）与所有依赖须在第一次可运行构建后锁定精确版本及校验值。
3. 训练端使用 dedicated server + 服务端假人，不启动完整游戏客户端，不生成 RGB 帧。
4. 自写 Fabric 训练桥接 mod；Carpet 只提供假人、动作和 tick 控制的参考基础，不是现成的 Gym 环境。
5. 默认一个人工可见的演示窗口，观察当前策略；大规模训练不随窗口帧率运行。
6. 从脚本基线和约 5M–30M 参数策略开始；模型规模是实验范围，不是已验证最优值。不把 1B、MoE、长记忆一次性实现作为起步条件。

## 2. 可观看训练：两个模式，而非所有环境渲染

### 2.1 默认模式：独立实时演示环境

训练进程持续进行无渲染采样和更新；另启动一个独立的 Fabric 演示服务端，以真实时间 20 TPS 运行。一个图形客户端进入演示服观战，演示假人使用最近发布的策略快照。

```text
无渲染训练服 × N ── 批量采样 ── Python 策略服务 / learner
                                      │
                              发布已完成更新的快照
                                      │
                             独立实时演示策略会话
                                      │
                             演示服：20 TPS + 假人
                                      │
                             一个图形客户端观战
```

- 这展示的是“当前模型能力”，**不是训练 worker 的实时画面**；界面必须标明 checkpoint 编号、训练步数、发布时间和演示种子。
- 建议按完成的若干次更新或每 30–120 秒发布一次快照；这是可调起点。模型发布应原子化，先写临时文件再重命名，不读取半写文件。
- 默认 episode 结束时切换模型，清空对应循环记忆，避免半局换权重污染演示；紧急停止可立即中断。
- 训练与演示必须使用相同 observation/action schema、物理版本和感知约束。演示输入不携带观战玩家位置。
- 观战客户端进入旁观者模式；相机跟随、第一人称附身（需实测假人视角）、第三人称和自由视角逐项验证。不能假设所有观战交互开箱即用。
- 旁观者不应成为怪物目标或改变任务奖励。旁观者可能影响区块加载等行为，演示世界应控制场地范围并验证其影响，不能只靠旁观模式声称零扰动。

独立演示环境的优势是画面正常速度、便于观看，也不会将训练服加速步进产生的抽搐画面误当模型失效。代价是多一份世界模拟；资源紧张时可关闭独立服，切换下述诊断模式。

### 2.2 诊断模式：直接观察一个训练 worker

在选定 worker 的 episode 边界暂停采样，将其降至 20 TPS 并允许客户端连接。此时明确将该 worker 从吞吐统计或主要训练池移出，不能声称仍维持原加速吞吐。需要复现时保存种子、初始状态、动作轨迹和策略版本。

不承诺仅凭世界种子完全复现：区块加载时序、随机状态和任务初始化同样需要控制。录制轨迹回放与实时策略演示应分别标识。

### 2.3 可视化初始设置

以下只是调优起点，不是已压测结果：

| 设置 | 初始建议 |
| --- | --- |
| 窗口 | 960×540 或 1280×720，不必全屏 |
| FPS 上限 | 30；有余量再提升到 60 |
| 渲染距离 | 6–8 chunks，按任务可见范围调整 |
| 画面 | Fast，无光影，减少粒子与云，保持亮度设置可审计 |
| 客户端堆 | 从 -Xmx2G 起，必要时到 3G；堆上限不等于进程总内存 |
| 优化模组 | 首先保持最小组合；再逐个验证与 1.20.1 匹配的 Sodium 等客户端模组 |

界面第一版只需要显示：当前任务、episode 回报、完成率、动作、checkpoint、训练样本数/秒、训练/演示状态。损失、资源与吞吐可放在本地仪表盘，不必全部做成游戏内 UI。慢思考文字若由模板或单独模块生成，需明确标识，不能冒充策略内部真实推理。

同卡训练和渲染会争夺显存与带宽；演示会话设置有界队列与超时，不能为等待 learner 而无限冻结实时游戏。若批量推理不能保证演示时延，应降低训练占用，或在小策略阶段测试独立 CPU 推理。

## 3. 训练环境与通信契约

服务端 mod 暴露概念接口（尚未实现，不是现有可调用 API）：

```text
reset(env_id, seed, task_config) -> observation, info
step_batch(actions, expected_tick_ids, repeat_ticks)
    -> observations, rewards, terminated, truncated, info
set_mode(env_id, train_accelerated | demo_realtime | paused)
close(env_id)
```

### 3.1 必须保证的语义

- 所有 Minecraft 世界读取与修改在正确服务端线程执行；网络线程只收发及排队，不直接异步访问世界。
- 规定一个 tick 内“动作应用—世界更新—观察与奖励计算”的顺序。每个结果附 env_id、episode_id、tick_id、schema_version、policy_version。
- 加速训练保留完整逻辑 tick 的游戏语义，只去除等待现实时间的部分；不能用瞬移替代移动、直接删除方块替代合法挖掘。
- 服务端暂停时，网络服务仍能接收下一批动作；避免控制线程与游戏线程相互等待。
- Carpet 的 freeze/step/warp 不能直接等同严格锁步接口；逐项测试玩家、生物、方块、流体、随机 tick 和区块任务后再复用或实现自己的控制层。
- 同一 MinecraftServer 的 tick 时钟是共享的。一个 JVM 内多个场地采用同步批次屏障，或明确实现并验证独立调度；不能宣称每个假人天然可以独立暂停和步进。单个场地 reset 期间也必须防止其他场地无动作漂移。
- terminated 与时间上限 truncated 分开；记录 repeat_ticks 的实际执行 tick 数。奖励折扣按 tick 或按决策步统一定义。
- 同一批复用一份策略权重，循环记忆和 KV 状态按 env/episode 隔离，不跨环境共享。

### 3.2 动作执行与公平性

基础动作包括方向按键、跳跃、疾跑、潜行、视角增量、攻击、使用、快捷栏及必要背包操作。必须实测斜向速度、潜行边缘、台阶、挖掘进度、攻击冷却、盾牌、弓、放置朝向和容器状态。Carpet 假人不是完整客户端物理与交互的自动等价物，关键任务需要真实客户端回归对照。

“原子合成、自动存箱、瞬移脱困、无限耐久”等只能作为显式助手模式能力；严格玩家模式禁止。两类轨迹、任务分数与模型配置分开，不能用助手模式结果声称完成原版玩家任务。

通信先实现批量本机 TCP 或 Unix socket 的二进制协议，加入长度与版本检查、超时和重连；Windows 兼容层可用 loopback TCP。先测量再决定是否实现共享内存，不以零拷贝作为首个里程碑。服务默认绑定本机，禁止将控制接口直接暴露公网。

## 4. 观察接口 V2：修正信息泄漏

1. 感知仅访问已加载区块；禁止感知调用触发远处区块生成。
2. 从眼位做有限 FOV、距离和遮挡判断；射线使用合适的方块形状，验证半砖、楼梯、栅栏、玻璃、树叶、流体。碰撞形状不天然等于视觉不透明性。
3. BFS 连通空气表层壳只可用于候选集或触觉计算，不能直接当视觉：绕拐角的墙面并不因与玩家空气连通就可见。
4. 亮度高不等于能辨认真正 ID；同外观方块合并，隐藏容器内容、矿石背面、实体 UUID 和世界随机状态不进入策略输入。
5. 听觉只基于实际产生的游戏声音事件，返回类别、粗略方向与距离/音量档位，不能扫描邻近实体后凭空构造声音雷达。
6. 主人、基地、敌人位置必须标注信息来源。远程主人精确位置是助手特权；严格模式只允许当前感知或带时间戳的历史记忆。
7. 光照清晰度公式只是近似，须标定黑暗、雾、失明、水下和不同距离；不宣称能严格模拟人类视觉。
8. 任何由特权世界状态计算的奖励或教师信息均与 actor observation 隔离，日志也分区。

先提供紧凑连续特征 + 类别 ID 的小模型基线，再与 2K 符号词表对比；不强制所有数值串行化成 token。256 条射线与 64 tokens/tick 的收益需做消融。空间射线方向应使用完整相机基向量构造，不能只把水平/垂直偏角简单相加而未验证几何误差。

数据必须记录存储层级：原始射线、压缩特征、符号帧或隐状态，不能混用体积估算。例如每帧保存 256×24 个 FP16 特征，在 20 Hz 下约为 0.885 GB/小时/环境（十进制，不含元数据），不是固定 50 MB/小时。

## 5. 12600K / 48GB / 16GB 的多开预算

### 5.1 压测档位而非承载承诺

| 档位 | 训练服 JVM | 每服场地/假人 | 训练环境总数 | 额外演示 |
| --- | --- | --- | --- | --- |
| A：正确性 | 1 | 1 | 1 | 先关闭；再测一个演示服+客户端 |
| B：并行基线 | 1 | 4 | 4 | 1 |
| C：多进程 | 2 | 4 | 8 | 1 |
| D：可选扩展 | 2 或 3 | 逐步增加 | 12–16 仅作为待测点 | 1，可关闭对比 |

12600K 不按逻辑线程数量线性推算环境数。Java 主线程、区块任务、Python 与渲染会同时争用 CPU；先让系统调度，再根据逐核利用率决定亲和性，避免未经测试硬绑性能核或能效核。

### 5.2 内存与显存起始政策

- 每个小场地训练服先设置约 2–4 GiB Java 堆上限，结合 GC 与 RSS 调整；不要一次给每个 JVM 分配大堆。
- 48GB 中先为系统、桌面与文件缓存预留约 8–10 GiB；Python、轨迹缓存、演示服、客户端和 JVM 非堆也必须计入。
- Python rollout/cache 明确设置容量上限，禁止无限积累 RGB 或隐状态；日志和 checkpoint 配额同样有上限。
- 整机可用内存持续低于约 8 GiB、发生持续 swap 或 GC 停顿显著上升时停止扩容。阈值是初始运维政策，需随系统实测调整。
- 有观战时，策略训练与推理的 CUDA 显存占用先以约 10–11 GiB 为软目标，给桌面、客户端与波动留余量；实际保留量依分辨率与模型实测。
- 先进行“采样阶段不反传、更新阶段暂停/限制采样”的分阶段循环，避免同卡 learner 与 actor 资源竞争；确有收益再做异步重叠。
- 两份模型副本、优化器、梯度、激活、循环状态、CUDA allocator 保留内存均入账。8-bit 优化器和混合精度不保证 1B 模型必定装下或运行更快。

区块预生成并保存场景模板；在本地 Linux 文件系统存储世界和数据。世界间距离隔离不能自动解决生物上限、时间天气等共享状态；独立评估用独立进程/世界配置，不把同服相关轨迹视为完全独立样本。

## 6. 模型与训练路线

### P0：环境正确性与观战闭环

实现一个假人、一种简单任务、reset/step 和实时演示。先用随机策略与手写策略跑通。人工观察假人动作，同时用自动测试检查合法速度、碰撞、挖掘及信息遮挡。

### P1：示范与小策略

用人工客户端或明确标识的脚本教师采集轨迹。教师可用寻路等额外信息，但学生输入始终走同一公平观察接口，记录 teacher_type。先行为克隆，再短任务 PPO 或其他明确选定的 RL 基线；验证序列 burn-in、记忆重置、动作掩码与价值 bootstrap。

任务从到点、绕障、跟随、砍树、拾取、放置、容器交互展开；跑酷与战斗保留更细动作频率。简单任务可测试动作保持 2–4 ticks，但必须正确处理期间奖励与终止。

### P2：CED 的可证伪对照

比较 GRU、小 Transformer 与小 CED，在相近参数、训练数据和计算预算下测成功率、吞吐、端到端延迟与长程回访。先做短窗，再做分层记忆；不能把神经记忆称为“永不遗忘”。只有明确收益后再扩大到更大模型；MoE 是后续选项，不是强制前提。

64 tokens/tick × 20 Hz = 每环境每现实秒 1280 个输入 token（真实时间运行时）；8 环境为 10240。动作头很小不代表编码器免费。测试帧内压缩、事件更新、多频率状态和历史摘要；加速仿真时按实际逻辑 tick 吞吐重新计算。

### P3：泛化与部署

种子、地图与任务布局分训练/验证/测试集合；记录失败轨迹与 checkpoint。关闭助手特权后单独验收严格玩家模式。真实客户端对照测试通过后，才宣称向原版玩家控制迁移有效。

## 7. 备选环境与渲染路线

| 方案 | 用途 | 决策 |
| --- | --- | --- |
| Fabric + Carpet + 训练 mod | 原版逻辑、无渲染训练 | 主路线 |
| Mineflayer | 教师、任务原型、快速行为验证 | 可选；低层时序与加速同步需单独验证 |
| CraftGround | 如果最终需要像素视觉输入 | 独立备选；其 MC 版本与主路线分别锁定 |
| Luanti + Mineclonia | 最终目标本身允许复刻游戏 | 可选分支，不默认迁移等价 |
| Craftax | 高吞吐探索、记忆与奖励研究 | 算法试验，不当成原版 3D 动作替代品 |

隐藏窗口、Xvfb 和离屏 FBO 都不代表没有渲染。结构化主路线不部署 Xvfb/VirtualGL/CUDA-OpenGL interop；仅人工观战客户端渲染。不要为省显存改成多路 CPU 软件渲染。

## 8. 首次部署顺序与验收

1. 核对 Ubuntu 形态、磁盘剩余、nvidia-smi、Java 17；记录 Python/PyTorch/CUDA 的实际兼容版本，不直接照抄未验证的最新依赖。
2. 启动本机绑定的 Fabric 1.20.1 服务端，安装匹配 Carpet，确认 EULA 与正版资源使用要求。人工客户端先验证连接与假人。
3. 实现训练 mod 与 Python 适配器；先不加优化模组。网络接口只监听本机；如为另一台机器观战，再显式配置防火墙与认证。
4. 依次验证移动/跳跃、挖掘/放置、容器、死亡重置、跨维度、冻结/步进；每项保存最小可复现实验。
5. 跑单环境脚本基线，再增加到 4、8 环境，测开启/关闭观战的差异。
6. 小模型 BC 与短任务 RL 成功后，接入实时演示快照；最后引入 CED 与记忆消融。

每档预热后至少记录一段稳态数据，重复多次，区分 reset/地形生成成本和稳态步进：

- aggregate env-ticks/s、决策 steps/s、有效样本/s、每环境吞吐与 reset 延迟；
- 游戏更新、感知提取、IPC、策略排队/推理的 P50/P95/P99；
- 任务成功率、每小时成功 episode 数、固定环境步数下的样本效率；
- 每 JVM RSS/GC、整机可用内存、CPU 各核利用率；
- GPU 利用率、显存 allocated/reserved、训练更新时长；
- 演示 FPS 与策略动作时延，checkpoint 更新是否成功。

完成标准：无渲染训练与一个可观看演示均可独立开关；无透视测试通过；多开无 episode/记忆串线；reset 可重复；无资源无限增长；README 的性能数字均可追溯到脚本、硬件和提交。**本次交付仅为上述实施规划，不声称这些标准已满足。**
